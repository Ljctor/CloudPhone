## 2. Modèle des comptes

Les comptes de connexion ne servent qu'à ouvrir une session puis à entrer dans
un compte fonctionnel :

| Compte | Connexion SSH | Délégation |
|---|---|---|
| `setup-agent` | clé uniquement | `system-setup`, `master` |
| `admin-human` | clé uniquement | `system-setup`, `master` |
| `emergency` | mot de passe uniquement | `system-setup`, `master` |

Comptes fonctionnels :

- `system-setup` : phases 1 et 2 ; sudo administratif ; mot de passe verrouillé ; pas de connexion SSH directe.
- `master` : phase 3 ; sudo administratif ; mot de passe verrouillé ; pas de connexion SSH directe.

Le compte fournisseur `debian` devait être supprimé à la fin de la phase 1,
après validation des connexions `setup-agent` et `admin-human`. Il ne devait
jamais être renommé.

`emergency` est le seul utilisateur autorisé à s'authentifier par mot de passe.
Son mot de passe existant doit être préservé. Aucun mot de passe par défaut ne
doit être créé pour lui. Les utilisateurs fonctionnels sans mot de passe sont
un choix volontaire et sûr puisqu'ils sont verrouillés, sans SSH direct, et
atteints uniquement via la délégation sudo contrôlée.

## 3. Phase 1 — Tout serveur

État cible encodé dans `runbooks/phase-1-any-server/` :

1. préflight Debian/systemd/OpenSSH/sudo ;
2. création et validation des comptes ;
3. clés SSH des comptes de connexion ;
4. bascule rapide de `debian` vers `setup-agent`, puis `system-setup` ;
5. audit des commandes ;
6. mot de passe SSH réservé à `emergency` ;
7. SSH sur le port personnalisé `52242` ;
8. pare-feu nftables, Fail2ban et LLMNR désactivé ;
9. outils Git/GitHub et fuseau `Europe/Paris` ;
10. vérification des états de mots de passe ;
11. retrait du compte bootstrap `debian`.

Audit : `auditd` enregistre les `execve/execveat` avec `auid >= 1000`. `auid`
permet de retrouver l'identité SSH initiale et `euid` le compte fonctionnel qui
a réellement exécuté la commande. L'audit des frappes clavier est volontairement
désactivé afin de ne pas capturer de secrets. Ne jamais passer un secret dans
les arguments d'une commande, car les arguments peuvent être audités.

## 6. Réseau

Architecture cible :

```text
Téléphone
  │ WireGuard UDP 51820
  ▼
Serveur 10.20.0.1/24
  ├── UI statique : TCP 8000, uniquement via wg0
  ├── passerelle : TCP 8001, uniquement via wg0
  ├── média WebRTC : UDP 32768-60999, uniquement via wg0
  ├── ADB : 127.0.0.1:5558
  └── gRPC Emulator : 127.0.0.1:8554
```

Le téléphone est le peer `10.20.0.2/32`. Le split tunnel utilise
`AllowedIPs = 10.20.0.0/24` et `PersistentKeepalive = 25`. Le port ADB et les
ports Web ne doivent jamais être ouverts sur l'interface publique.

## 8. Application WebRTC

Services :

- `android-emulator-web.service` : fichiers statiques sur le port 8000 ;
- `android-emulator-gateway.service` : REST + WebSocket JSEP sur le port 8001 ;
- sources déployées sous `/opt/android-emulator-web`.

Chemin du flux :

```text
Firefox téléphone
  ├── HTTP UI :8000
  ├── WebSocket JSEP :8001
  ├── WebRTC vidéo/audio ← Android Emulator VideoBridge
  └── REST touch/key :8001 → EmulatorController gRPC/ADB
```

La couche REST de contrôle est une personnalisation locale. Les coordonnées
tactiles sont transformées depuis le rectangle vidéo affiché vers l'écran
Android natif 540 × 1170. La barre de contrôle est verticale, à droite de
l'écran, pour ne masquer aucune zone tactile. Les contrôles relatifs au Web
(`↻` et indicateur) sont séparés des boutons Android.

Le clavier Android est géré par Android lui-même. Ne pas réintroduire de bouton
custom pour un clavier flottant.

## 9. Cause et correction des écrans noirs

Plusieurs défauts distincts ont été corrigés :

1. L'offre SDP était créée des deux côtés. Le client attend maintenant l'offre
   autoritaire envoyée par l'Emulator, ce qui évite l'offer glare.
2. La passerelle envoyait un second message `start` synthétique. Il a été retiré.
3. Les anciennes sessions fermaient le WebSocket sans envoyer le message JSEP
   `{"bye": true}`. Elles restaient orphelines et entraient en concurrence avec
   la session suivante.
4. La passerelle envoie aussi un `bye` de secours si un onglet est tué ou perd
   sa connexion sans pouvoir fermer proprement.
5. Les événements `visibilitychange` et `pageshow` pouvaient provoquer des
   reconnexions concurrentes. Le reset est maintenant sérialisé ; les demandes
   simultanées sont ignorées.
6. L'indicateur passait au vert dès la réception d'une piste WebRTC, même sans
   trame. Il ne passe désormais au vert qu'après une vraie trame décodée
   (`loadeddata`/`playing`). Une attente temporaire sur un écran statique conserve
   la dernière image au lieu de remettre un voile de chargement.

Sémantique finale :

- fond gris + spinner + orange : l'application Web négocie ou attend sa première trame ;
- vert : le navigateur a réellement décodé une image ;
- vert + écran noir : Android lui-même rend du noir ;
- le bouton `↻` détruit complètement la session WebRTC, attend une seconde,
  puis crée exactement une session neuve ; il ne redémarre ni Android ni le jeu.

Après un déploiement Web, fermer complètement l'ancien onglet mobile puis
rouvrir l'URL. Un paramètre de cache temporaire peut être ajouté, par exemple
`?v=<hash-du-bundle>`, afin d'éviter de réutiliser le JavaScript gardé en mémoire.

## 11. Dépannage et pièges connus

- Le registre npm local peut pointer vers un miroir privé qui retourne `403`.
  Utiliser explicitement `--registry=https://registry.npmjs.org/` ou
  `npm_config_registry=https://registry.npmjs.org/` pour les dépendances publiques.
- Playwright doit tourner sur le serveur avec `--network host`, car le navigateur
  local n'a pas forcément accès aux candidats média WebRTC protégés par WireGuard.
- Une piste WebRTC `live` et un ICE `connected` ne prouvent pas qu'une image a
  été décodée. Inspecter `video.readyState`, `videoWidth/videoHeight` et les
  compteurs `inbound-rtp.framesDecoded`.
- Ne pas conclure qu'une phase est terminée depuis ce document. Les runbooks
  suivent Check → Apply si nécessaire → même Check.
- Ne pas redémarrer l'émulateur pour un simple problème d'interface Web.
- Ne jamais faire de rollback Git destructif : le worktree contient des runbooks non commités.

## 12. Accès SSH local

Le client local utilise un alias dans `~/.ssh/config`, le compte
`setup-agent`, le port `52242`, la clé dédiée
`~/.ssh/id_ed25519_to_my_own_servers` et le socket systemd
`/run/user/1000/openssh_agent`.

La clé privée est chiffrée. Un accès filesystem complet ne permet pas de
contourner sa passphrase. Elle doit être chargée dans l'agent via une invite
locale protégée. Ne jamais coller la passphrase dans un chat ou une commande.

Chemin administratif habituel après connexion :

```sh
sudo -n -u master sudo -n <commande>       # phase 3
sudo -n -u system-setup sudo -n <commande> # phases 1 et 2
```
